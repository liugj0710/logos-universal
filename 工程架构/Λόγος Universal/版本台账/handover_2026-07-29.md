## 三、已知事实问题（3 个，待修复）

### 3.1 问题 1：Bing/Baidu 网页搜索死循环（最高优先级）

**现象**: `TabPool:baidu 浏览器启动失败: 'Chromium' object has no attribute '_dl_mgr'`，随后 TabPool 进入"启动→失败→重建"死循环，阻塞 Retrieve 的 `asyncio.gather` 120 秒超时。

**根因**: DrissionPage 库版本与当前 Chrome 浏览器不兼容。

**当前 workaround**: `api/retrieve.py` 中已**临时注释掉** Bing 和 Baidu 搜索任务，仅保留 Chroma + Dify KB。代码中有明确注释标记：
```python
# 2026-07-29: 临时禁用 Bing/Baidu 网页搜索（浏览器启动循环问题待修复）
```

**修复方案**: 
1. 在机械革命上执行 `pip install --upgrade DrissionPage`
2. 检查 Chrome 是否安装且路径正确
3. 确认端口 9223/9226 无残留进程占用
4. **恢复** `api/retrieve.py` 中被注释的两行搜索任务
5. 重新运行 E2E 测试验证 Retrieve 能在 30 秒内完成

**注意**: 恢复网页搜索后，需确认 `source_stats` 中 Bing/Baidu 有返回结果，且不会再次触发死循环。

---

### 3.2 问题 2：Citation Validator content_mismatch 阈值敏感

**现象**: E2E 测试中每个用例都有 3-7 个 `content_mismatch`（high severity），导致 `valid=False`。

**根因**: LLM 在生成报告时对原文进行了概括性改写（如"设备完好率应达到90%以上"被改写为"设备完好率≥90%"），而 `_fuzzy_match` 的清理逻辑（去除所有标点+空白）导致相似度低于 0.5。

**当前状态**: 不是系统故障，是 LLM 生成行为的正常表现。`missing_source=0` 证明引用来源真实存在。

**修复方案（可选）**:
- 方案 A: 将 `_fuzzy_match` 的判定阈值从 0.5 降至 0.3（在 `core/citation_validator.py` 中修改）
- 方案 B: 在 `core/synthesize.py` 的系统提示词中增加"引用摘录必须尽量贴近原文，允许小幅改写但核心数据不得变更"
- 方案 C: 两者结合

**注意**: 修复后需重新跑 `test_phase3_e2e_power.py` 验证 `content_mismatch` 数量下降，但不可降至 0（LLM 必然会改写）。

---

### 3.3 问题 3：Citation Validator missing_citation（章节漏引）

**现象**: 每个用例都有 1-6 个 `missing_citation`，即某些 section 没有 citation 列表。

**根因**: LLM 在生成某些章节时未按提示词要求添加 `citations` 字段。

**当前状态**: 非阻塞问题，报告内容本身正确。

**修复方案（可选）**: 在 `core/synthesize.py` 的系统提示词中强化：
```
每个章节（sections 中的每个对象）必须包含 "citations" 字段，且至少包含一个 citation。
如果该章节的信息来自多个 chunk，请列出所有相关 citation。
```
